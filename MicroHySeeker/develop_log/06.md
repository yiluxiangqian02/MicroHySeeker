## 问题 2：电化学多步骤报错和泵问题

### 用户报告
```
[20:48:41] ✓ 步骤 1 [电化学] 完成
[20:48:41] ▶ 步骤 2 开始: [电化学] LSV, E0=0.00V, 扫速=0.05V/s, 灵敏度=0.1
[20:48:41] [步骤1] 开始执行: echem
[20:48:41] [错误] unsupported format string passed to NoneType.__format__
[20:48:41] ✗ 步骤 2 [电化学] 失败
[20:48:41] [步骤1] 执行失败
[20:48:41] 实验异常结束

目前当我有多个电化学工作站的测试 或者要多次使用电化学工作站的时候好像就会报错；而且泵也出现了问题
```

### 根因分析

通过 subagent 深度分析，发现 **6个Bug**：

#### Bug 1（直接原因）：LSV 参数格式化 NoneType 崩溃
**文件**: `runner.py` 第722行
**问题**: `ec.eh:.2f` 当 `eh=None` 时报 `unsupported format string passed to NoneType.__format__`
**根因**: CV 和 LSV 共用一个参数模板，但 LSV 不需要 Eh/El

#### Bug 2：CHI Bridge 失败/异常时未清理
**文件**: `runner.py` `_execute_echem()`
**问题**: 成功路径关闭了 CHI 660F，但失败和异常路径直接 `return False`，Bridge 泄露
**后果**: 下次 echem 时 stale 实例导致冲突

#### Bug 3：信号先于紧急停泵
**文件**: `runner.py` `run()` 方法
**问题**: `experiment_finished.emit()` 在 `_emergency_stop_all_pumps()` **之前**发射
**后果**: UI 已重置但泵还在转

#### Bug 4：位置模式泵完成未校验
**文件**: `runner.py` `_execute_prep_sol()`
**问题**: 发送位置命令后只按时间估算等待，不验证泵是否真的停了
**后果**: 如果估算偏短，泵在进入下一步（echem）时仍在运动

#### Bug 5：批次中部分泵失败不清理
**文件**: `runner.py` `_execute_prep_sol()`
**问题**: 同批次中第2个泵启动失败时，第1个已启动的泵不被停止
**后果**: 已启动的泵继续运行

#### Bug 6：RESPONSE_UNSTABLE_PUMPS 硬编码散落
**文件**: `rs485_wrapper.py`
**问题**: 三处独立定义 `[1, 11]`，修改时容易遗漏
**改进**: 提升为类常量

## 问题 3：批次内泵并发时状态指示灯不更新

### 用户报告
```
目前有一个bug：就是可能同时会并发很多泵，然后有些泵是早结束，有些是晚结束；那么早结束的泵停止了；但是主界面的图形还是绿色的 没有更新
```

### 根因分析
批次内多泵同时启动后，只在开头发射了一次 `pump_batch_update`（全部绿色），然后整个批次等待期间没有再更新，导致早完成的泵仍显示绿色。

### 修复方案（第一版）

**文件**: `src/engine/runner.py`

**修改**: 在等待循环中定期轮询各泵实际运行状态

```python
# 等待本批次中最长的泵完成
if max_wait > 0:
    self.log_message.emit(f"    等待批次 {order_num} 完成... ({max_wait:.1f}s)")
    # 分段等待，支持中途停止，并实时更新泵状态指示灯
    waited = 0.0
    still_running = set(t["pump_addr"] for t in batch)
    poll_counter = 0
    while waited < max_wait:
        if self._stop_flag:
            for t in batch:
                self.rs485.stop_pump(t["pump_addr"])
            return False
        step_wait = min(0.5, max_wait - waited)
        time.sleep(step_wait)
        waited += step_wait
        
        # 每 ~1.5s 轮询一次各泵运行状态，更新 UI 指示灯
        poll_counter += 1
        if poll_counter % 3 == 0 and still_running:
            newly_done = []
            for addr in list(still_running):
                if not self.rs485.is_pump_running(addr):
                    newly_done.append(addr)
                    still_running.discard(addr)
                time.sleep(0.15)  # 总线间隔
            
            if newly_done:
                # 有泵完成 → 重新发送状态更新
                self.pump_batch_update.emit(
                    list(still_running), waiting_addrs
                )
                for addr in newly_done:
                    sol = next((t["sol_name"] for t in batch if t["pump_addr"] == addr), f"泵{addr}")
                    self.log_message.emit(f"    ✓ 泵 {addr} ({sol}) 已停止")
```

### 用户反馈
```
目前当泵停止后其实还是没有更新状态  目前的主界面的形状还会是绿色的
```

### 根因分析（深入）
发现问题不在轮询逻辑，而在：
1. **批次等待结束后没有发射 `pump_batch_update`** — 最后一次轮询和循环退出之间停止的泵，绿灯残留
2. **所有批次结束后没有发射清零信号** — 最后一个批次结束后，所有泵绿灯残留到步骤完成才清

### 修复方案（最终版）

**文件**: `src/engine/runner.py`

**修改 1**: 批次等待结束后清除本批次指示灯
```python

                # 有泵完成 → 重新发送状态更新

                    list(still_running), waiting_addrs
                )

# 批次等待结束 → 清除本批次所有运行指示（剩余的绿灯归灰）

# 停止RPM时间模式的泵
```

**修改 2**: 所有批次完成后全部清零
```python

        time.sleep(0.5)

# 所有批次完成 → 清除全部泵指示灯
```

## 技术要点总结

### RS485 半双工总线竞争
- **问题**: 多泵连续发送命令导致总线冲突
- **解决**: 命令间插入 150ms 间隔
- **特殊处理**: 泵1/11 响应不稳定，使用 fire_and_forget

### 位置模式编码器闭环
- 位置模式有编码器反馈，泵会自行运动到目标位置
- **关键**: 使用 `read_run_status()` 轮询确认真正完成
- **超时处理**: 强制停止 + 警告日志

### Qt 信号发射时序
- **原则**: 硬件操作 → 数据保存 → UI 信号
- **反例**: 信号先发射，UI 重置，但硬件还在运行
- **正例**: 先停泵、保存数据，最后 emit 信号

### CHI Bridge 资源管理
- **问题**: 失败/异常路径资源泄露
- **解决**: try-finally 模式确保清理
- **好处**: 避免 stale 连接导致下次运行失败

### 实时状态更新策略
- **轮询间隔**: ~1.5s（poll_counter % 3）
- **总线间隔**: 查询命令间 150ms
- **信号优化**: 仅在状态变化时 emit，避免无效刷新

## 遗留问题和未来改进

### 1. Mock 模式泵状态模拟
当前 Mock 模式的 `read_run_status` 始终返回 `1`（停止），导致：
- 实时轮询会在第一次就检测到"全部停止"
- 真实硬件测试前无法验证轮询逻辑

**改进方向**:
- Mock 模式维护泵运行时间表
- `read_run_status` 根据经过时间返回对应状态

### 2. 泵状态查询频率优化
当前每 1.5s 轮询所有仍在运行的泵，12 个泵并发时：
- 12 × 150ms = 1.8s 总线占用

**改进方向**:
- 自适应轮询间隔
- 优先轮询接近完成时间的泵

### 3. 位置完成超时处理
当前超时后强制停止 + 继续执行，可能导致：
- 目标体积未注入完全
- 下游步骤的浓度偏差

**改进方向**:
- 超时后询问用户：重试/继续/中止
- 记录实际运行时间和推测位移量

### 4. CHI Bridge 状态持久化
当前每次 echem 都创建/销毁 Bridge，开销较大

**改进方向**:
- Runner 级别维护单例 Bridge
- 仅在实验开始/结束时 connect/disconnect
- 步骤间复用连接
