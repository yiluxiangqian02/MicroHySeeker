```python
def scan_devices(self, addresses: list[int] | None = None, 
                 timeout_per_addr: float = 0.3, retries: int = 5) -> list[int]:
    online_pumps = []
    for addr in addresses:
```

**修改后**:
```python
def scan_devices(self, addresses: list[int] | None = None, 
                 timeout_per_addr: float = 0.3, retries: int = 5) -> list[int]:
    # 已知响应异常但通常能工作的泵列表
    RESPONSE_UNSTABLE_PUMPS = [1, 11]
    
    online_pumps = []
    for addr in addresses:
        is_detected = False
        try:
            frame = self.request(addr, CMD_SPEED, payload=payload, 
                               timeout_s=timeout_per_addr, retries=retries)
            if frame is not None:
                is_detected = True
                self._logger.debug(f"泵 {addr} 在线 (响应正常)")
        except TimeoutError:
            self._logger.debug(f"泵 {addr} 扫描超时 (经 {retries} 次重试)")
        
        # 如果正常检测到了，或者是已知的响应异常但能工作的泵，都认为在线
        if is_detected or addr in RESPONSE_UNSTABLE_PUMPS:
            online_pumps.append(addr)
            if not is_detected and addr in RESPONSE_UNSTABLE_PUMPS:
                self._logger.debug(f"泵 {addr} 在线 (已知响应异常但可控制)")
    
    return online_pumps
```

**关键改进**:
- 添加 `RESPONSE_UNSTABLE_PUMPS = [1, 11]` 常量
- 即使扫描超时，泵1和11也会被标记为在线
- 添加详细的日志输出区分检测方式

### 第七步：发现并修复严重BUG

**用户问题 #3**:
> 你刚刚在运行的时候出现了一个很危险的情况，能转的特别快；
> 但是现在我能够在扫描泵中扫描到1，但是手动控制中控制失败

**问题分析**:

我检查了测试代码，发现了一个**严重的参数顺序错误**：

```python
# 错误的调用 (test_scan_pump1.py)
start_result = driver.run_speed(1, True, 100)  # ❌ 危险！

# run_speed 的正确签名
def run_speed(self, addr: int, rpm: int, forward: bool = True) -> bool:
```

**问题严重性**:
- `True` 被当作 `rpm` 参数，转换为整数 1
- `100` 被当作 `forward` 参数
- 实际发送的速度只有 1 RPM（几乎不动）或者参数混乱导致异常高速

**同时发现的第二个问题**:

PumpManager的fire_and_forget模式使用了错误的方法：

```python
# 错误的实现
self.driver.write(build_frame(addr, CMD_ENABLE, payload))  # ❌

# 正确的实现
self.driver.send_frame(addr, CMD_ENABLE, payload)  # ✅
```

**原因**: `RS485Driver` 没有直接的 `write()` 方法接收完整帧，应该使用 `send_frame()`

## 技术总结

### 核心解决方案：Fire-and-Forget模式

**设计理念**:
- 对于能接收命令但不能正常响应的设备，采用"发送后不等待"策略
- 避免UI因等待超时而卡顿
- 提高用户体验

**实现要点**:

1. **参数设计**: 在所有控制方法中添加 `fire_and_forget: bool = False` 参数
2. **硬编码识别**: 使用常量 `RESPONSE_UNSTABLE_PUMPS = [1, 11]` 明确标识问题设备
3. **分层实现**: 
   - 底层: PumpManager 提供 fire_and_forget 选项
   - 中间层: RS485Wrapper 自动判断并使用
   - 上层: 前端透明调用，无需关心底层细节

4. **扫描策略**: 即使设备不响应，也标记为"已知响应异常但可控制"

### 修复的关键BUG

1. **参数顺序错误**: `run_speed(addr, rpm, forward)` 
2. **方法调用错误**: `write()` → `send_frame()`
3. **逻辑判断错误**: 基于扫描结果 → 硬编码设备列表

### 测试策略

**三级测试体系**:
1. **Mock模式测试**: 验证逻辑正确性
2. **扫描功能测试**: 验证设备检测
