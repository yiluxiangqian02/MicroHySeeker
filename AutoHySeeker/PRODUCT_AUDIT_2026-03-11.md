# AutoHySeeker Web 产品审计报告（2026-03-11）

## 一、审计结论

当前 AutoHySeeker Web 已经具备一个“控制台”雏形，但离最初设想的 **AI 实验管家（Experiment Steward）** 还有明显偏差。现在更像：

- 一个把“系统状态 / Agent / 模板 / 设置”并列展示的开发者后台；
- 一个用 AI 术语堆砌的能力展示页；
- 一个以技术组件组织页面，而不是以科研任务组织流程的产品。

这导致三个核心问题：

1. **用户进来不知道先做什么**：缺少面向科研流程的主入口。
2. **Agent 功能定义难理解**：内部编号、技术分工、用户价值没有对齐。
3. **实验创建与执行难用**：围绕参数表单组织，而不是围绕“实验意图 → 方案 → 执行 → 结果”。

---

## 二、与最初期待的偏差

### 1. 产品定位偏差：从“实验管家”退化成“系统控制台”

初始文档强调的是：

- 覆盖 **实验前规划 → 实验中监控 → 实验后分析** 全流程；
- 先做 L1/L2 的实用价值，再逐步演进到 L3；
- AI 的核心价值是 **帮助科研人员完成任务**，不是展示 Agent 架构。

但当前 Web 的主导航和首页信息架构，优先级却是：

- Overview
- Dashboard
- Agents
- Templates
- Settings

这是一套典型“系统后台”视角，不是“科研工作流”视角。

### 2. 信息架构偏差：按技术模块分，而不是按科研任务分

当前页面是按系统模块切：

- 总览
- 监控
- Agent 控制
- 模板
- 设置

而不是按真实科研任务切：

- 我要开始一个新实验
- 我要盯住正在跑的实验
- 我要看结果并分析
- 我要让 AI 给我建议/诊断
- 我要复用历史模板/经验

结果是用户必须先理解系统架构，才能完成科研任务，这和“降低认知负担”的目标相反。

### 3. 能力成熟度偏差：L3 叙事过多，L1/L2 交付感不足

初始文档非常明确：**不要一步到位做 Multi-Agent，要先把 L1/L2 工具打实**。

但当前产品中：

- “Agent 控制”存在感过强；
- 首页强调系统、Agent、健康状态；
- 智能建议、聊天等功能很多仍是 stub/mock；
- 实际对科研用户最重要的“实验创建、运行、结果解读”没有形成清晰闭环。

这会让用户以为系统很智能，但真正使用时感到落差。

---

## 三、为什么 Agent 功能定义难理解

### 1. 命名站在开发视角，不站在用户视角

当前同时存在：

- C1 / C2 / C3 / D2 / D3 这类内部编号；
- 数据分析 / 故障诊断 / 实验设计 / 实验监控 / 知识管理等技术标签；
- Chat 中又出现 data_analyst / experiment_designer / knowledge_manager 等另一套名称。

问题：

- 一套系统里有 **三套命名体系**；
- 用户不知道这些 Agent 与自己要完成的任务是什么关系；
- “监控 / 诊断 / 设计 / 分析 / 知识”边界对用户来说并不天然清晰。

### 2. 缺少“什么时候用它”的解释

Agent 页面现在主要展示：

- 状态
- token
- 响应时间
- 日志

但普通科研用户真正关心的是：

- 我遇到什么问题时该找谁？
- 它能替我完成什么？
- 输入什么问题，能得到什么输出？

也就是说，缺少 **任务场景描述**，只有 **系统运行指标**。

### 3. 产品把“多 Agent 架构”暴露得太早

初始文档里 Multi-Agent 是实现架构，不是用户心智模型本身。

对于用户，更自然的表达应该是：

- AI 实验助手
- AI 数据分析师
- AI 故障排查助手
- AI 方案建议助手

而不是先让用户理解 Agent 编队和控制面板。

---

## 四、为什么实验部分难用

### 1. 创建实验是“参数编辑器”，不是“实验任务向导”

当前创建实验对话框主要让用户：

- 填名称
- 填描述
- 加 step
- 每步选择 CV/EIS/CA…
- 逐项填参数

这更像给熟悉电化学参数的人准备的 JSON 表单编辑器，而不是产品级实验创建流程。

缺失了三个关键引导：

1. **实验目的**：我要做筛选、标定、验证、对照，还是故障复查？
2. **推荐起步方案**：如果我是第一次做 CV，系统给我什么默认值？
3. **执行前检查**：这个方案大概多长时间、有哪些风险、是否适合当前设备状态？

### 2. 页面语言偏“技术字段”，缺少科研语义

例如：

- step_type
- params
- create experiment
- execute experiment

这些词是工程语言，不是科研场景语言。用户需要的是：

- 测什么
- 为什么这样测
- 大概多久
- 结果出来后看什么

### 3. 实验详情页过于扁平

当前详情页有：

- 实验信息
- 步骤
- 数据图

但缺少科研人员更需要的结构：

- 本次实验目的
- 当前状态 / 下一步
- 关键参数摘要
- 结果摘要
- AI 初步解读
- 如果失败，给出最可能原因与下一步建议

### 4. 执行与分析断裂

从“创建 → 执行 → 结果 → 建议”之间缺少明显的连续动作：

- 创建后只是进入详情；
- 执行后没有稳定的“运行中视图”承接；
- 分析最近实验、获取建议是首页零散按钮，不是实验闭环的一部分。

## 五、后端与产品表达的偏差

### 1. 多个核心能力仍是 stub / mock / 内存态

当前可见问题：

- experiments 使用内存 store，重启丢数据；
- suggestions 返回占位内容；
- chat 依赖关键词分类 + mock response；
- agent control 主要是 mock 数据与控制台式展示。

这说明产品叙事已经跑到能力前面了。对用户来说，这会损害信任。

### 2. API 组织有“研发演示痕迹”

接口具备原型验证价值，但尚未围绕稳定产品对象建模，例如：

- experiment 的生命周期状态不完整；
- 缺少“实验摘要 / 结果摘要 / AI 结论 / 失败原因”等一等公民字段；
- chat 与 experiment/context 之间绑定较弱。

## 六、建议的产品级重构方向

## 1. 重构信息架构：从“系统模块”切换到“科研流程”

建议主导航调整为：

1. **开始实验**（新建 / 从模板创建）
2. **运行中**（实时监控、告警、停止）
3. **实验记录**（历史实验、详情、对比）
4. **AI 助手**（建议、诊断、问答）
5. **模板与设置**（低频配置）

如果短期不改路由，至少先改页面文案与首页入口，让用户看到的是任务流而不是系统流。

## 2. 重构 Agent 表达：从“内部组件”改为“用户可调用角色”

建议把 Agent 重新包装为用户角色：

- **数据解读助手**：看结果、找趋势、做对比
- **实验设计助手**：推荐参数、补齐方案
- **运行监护助手**：盯住实验进展和异常
- **故障排查助手**：解释失败原因和排查路径
- **知识助手**：检索历史经验与方法

并且每个角色都回答三件事：

- 什么时候找它
- 它会输出什么
- 一个具体示例问题

## 3. 重构实验创建：从“填表”改成“意图驱动”

实验创建建议改成 4 步：

1. **你想做什么实验？**（筛选 / 标定 / 验证 / 复现 / 故障复查）
2. **选择方法**（CV / EIS / CA / DPV…）
3. **确认关键参数**（只先暴露必要参数）
4. **执行前检查**（时长、风险、设备状态、建议）

高级参数默认折叠是对的，但还需要“推荐默认值 + 为什么这样设”。

## 4. 重构首页：从“状态大盘”变成“实验工作台”

首页应该首先回答：

- 今天系统能不能跑？
- 我下一步最应该做什么？
- 最近一次实验发生了什么？
- AI 能帮我继续什么动作？

而不是先展示 CPU、memory、agent 数量。

## 5. 重构实验详情：变成真正的“实验工作页”

建议把详情页分成 5 块：

- 实验目的与状态
- 关键参数摘要
- 运行轨迹 / 原始数据
- AI 结果解读
- 下一步动作（重跑 / 对比 / 生成建议 / 故障排查）

## 七、分 Phase 落地计划

### Phase 1：先解决“看不懂”（1~3 天）

目标：不动大架构，先把认知负担降下来。

- 改导航文案：弱化“Agent 控制”，强化“AI 助手分工”
- 改首页首屏：加入“AI 实验管家”的任务入口与科研流程说明
- 改 Agent 页面：把内部能力翻译成用户能理解的角色说明
- 改创建实验对话框：加入实验目的提示、推荐起手方式、参数解释
- 改实验详情页标题与操作文案：更贴近科研语义

### Phase 2：再解决“难用”（3~7 天）

目标：让创建 → 执行 → 查看结果更顺。

- 新建实验改为向导式流程
- 增加“推荐模板 / 常见场景”入口
- 执行后自动跳转到运行中视图
- 实验详情增加参数摘要、结果摘要、下一步动作
- 首页和详情页打通“分析 / 诊断 / 建议”闭环

### Phase 3：补足产品真实感（1~2 周）

目标：减少“演示感”，提升信任。

- experiments 改为持久化存储
- suggestions 接入真实分析/推荐逻辑
- chat 绑定 experiment context，而不是通用 mock
- agent 状态接真实 API，去掉大量 mock 数据

### Phase 4：逐步逼近“实验管家”（后续）

- 实验前方案审查
- 实验中异常解释与干预建议
- 实验后自动总结与下一步推荐
- 跨实验对比与知识沉淀

## 八、本次建议优先级

### 必须先做

1. 首页改成任务入口
2. Agent 改成角色化表达
3. 实验创建增加引导与默认路径

### 可以随后做

1. 模板体系分场景整理
2. 聊天窗改成“当前实验上下文助手”
3. 监控页改名并与执行流打通

### 暂时不要优先做

1. 继续扩 Agent 控制面板细节
2. 继续堆系统状态图表
3. 继续增加未落地的高级 AI 叙事
