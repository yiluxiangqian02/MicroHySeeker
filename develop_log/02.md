### 5. 第四阶段：实际执行问题排查

**用户报告**: 
> 你现在的方法好像遇到了问题我直接打开exe是可以正常使用可以打开的 好像你现在的方法打开会直接报如图 所以你要想想办法

**截图显示**: Microsoft Visual C++ Runtime Library Error

**我的排查思路（详细说明）**:

#### 5.1 问题假设（按概率排序）

1. **工作目录(cwd)错误** (最可能)
   - 双击 exe: Windows 自动设置 cwd = exe 所在目录
   - subprocess 默认: cwd = Python 脚本目录
   - MFC 程序启动时相对路径查找 `chi660f.cfg`/`chi660f.ini`/`.bin` 技术模板
   - 找不到依赖文件 → C++ Runtime abort() → Runtime Error

2. **/runmacro 参数本身问题**
   - 参数格式错误
   - 宏文件路径中有中文字符（老 MFC ANSI 编码问题）

3. **环境变量差异**（概率低）

#### 5.2 分步诊断脚本 `diag_chi660f.py`

**Step 1**: subprocess + cwd=exe目录 + 无参数
```python
subprocess.Popen([EXE_PATH], cwd=EXE_DIR)
```
**结果**: ✅ **成功** — 进程 5 秒后仍在运行（GUI 正常打开）

**结论**: 设置 `cwd=exe目录` 后 exe 可以正常启动，**Runtime Error 根因确认是 cwd 缺失**

**Step 2-4**: 测试 /runmacro 参数

## 经验教训

1. **老旧 MFC 程序的坑**:
   - ANSI 编码无法处理中文路径（必须纯 ASCII）
   - 相对路径依赖工作目录（subprocess 必须设 cwd）
   - 配置文件（cfg/ini）和模板文件（.bin）必须在同目录

2. **命令行参数传递陷阱**:
   - Windows 下引号、空格、特殊字符的处理极其复杂
   - subprocess 的 list vs string 模式行为差异大
   - shell=True 时要特别注意路径转义

3. **诊断策略**:
   - 分步排查（从最简单开始: 纯启动 → 带参数 → 完整功能）
   - 用 BAT 文件排除编程语言本身的干扰
   - 记录每一步的退出码、运行时间、现象

4. **备选方案的重要性**:
   - 命令行方案不可用时，GUI 自动化（pywinauto/Sikuli）是可靠后备
   - 甚至可以考虑 DDE 通信（CHI 老软件可能支持）
